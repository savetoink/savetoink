1. The Actors

ActorRole
Browser The user's browser running the SvelteKit webapp. Stores tokens in httpOnly cookies.
Backend Go HTTP server. Validates PASETO tokens locally — no external call needed per request.
Auth0 Identity provider. Only involved during initial login — never sees PASETO tokens.
Key idea: Auth0 is the identity provider. PASETO is the token format between backend and browser. The browser never sees or handles Auth0 JWTs — only opaque v4.local.* PASETO tokens.

2. Login Flow (Authorization Code Exchange)

This happens once when the user clicks "Log In".

Browser → Auth0 GET /authorize (redirect user to Auth0 login page)
· · · user authenticates on Auth0 · · ·
Auth0 → Browser 302 → /auth/callback?code=abc123
· · · · · · · · · · · · · · · · · · ·
Browser → Backend POST /v1/auth/token { code, redirect_uri }
Backend → Auth0 POST /oauth/token { code, client_secret }
Auth0 → Backend { access_token (JWT), id_token (JWT) }
· · · backend swaps JWTs for PASETO · · ·
Backend extracts sub + email from Auth0 JWTs, generates PASETO pair
Backend → Browser { access_token, refresh_token, email, expires_in: 3600 }
SvelteKit callback stores → auth cookie (access, 1h) + refresh cookie (refresh, 7d)
Result: The browser now has two httpOnly cookies. The Auth0 JWTs are discarded — they never reach the browser.

3. Authenticated Request

Every API call (list articles, send article, etc.) follows this pattern. No external call — validation is local.

Browser → Backend GET /v1/articles · Cookie: auth=v4.local.xxx
SvelteKit hooks read auth cookie → pass as Authorization: Bearer v4.local.xxx
Backend middleware: decrypt PASETO with local symmetric key → extract account_id
Backend → Browser 200 { articles: [...] }
No JWKS fetch, no Auth0 call. PASETO v4.local uses symmetric encryption (XChaCha20-Poly1305). The backend validates tokens with a single local key — fast and self-contained.

4. Token Refresh (Automatic)

When the access token expires (1h), the SvelteKit server hooks detect the failure and automatically refresh.

Browser → Backend GET /v1/articles · Cookie: auth=v4.local.EXPIRED
Backend → Browser 401 Unauthorized
· · · SvelteKit hooks catch the 401 · · ·
SvelteKit server → Backend POST /v1/auth/refresh { refresh_token }
Backend validates refresh token → generates fresh access + refresh pair
Backend → SvelteKit server { access_token, refresh_token, expires_in: 3600 }
Hooks update both cookies → retry the original request → user never notices
If the refresh token is also expired (7 days), both cookies are cleared and the user is redirected to the login page.

5. Logout

Browser → Backend POST /account ?/clean
SvelteKit action: delete auth cookie + delete refresh cookie
If Auth0: redirect to Auth0 /logout endpoint
If SharedKey: redirect to /account

6. Token Details

PropertyAccess TokenRefresh Token
Format v4.local.<encrypted> v4.local.<encrypted>
TTL 1 hour 7 days
Stored in auth httpOnly cookie refresh httpOnly cookie
Sent as Authorization: Bearer v4.local.* JSON body to /v1/auth/refresh
Encryption XChaCha20-Poly1305 + BLAKE2b-MAC (PASETO v4.local)

Token Claims (encrypted inside)

{
  "sub":   "auth0|abc123",     // account ID from Auth0
  "email": "user@example.com",
  "key_version": "v1",         // which symmetric key encrypted this
  "token_type":  "access",     // or "refresh"
  "iat": 1744900000,           // issued at
  "nbf": 1744900000,           // not before
  "exp": 1744903600            // expiration
}
